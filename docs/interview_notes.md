## 第一部分：项目本身

### Q1. 一句话介绍这个项目

**答**：一个面向中国 A 股上市公司年报的 RAG 问答系统，把「下载 → PDF 解析 → 分块 → 向量化 → 混合检索 → 重排 → 生成 → 评估」全链路按企业级标准实现了一遍。语料是巨潮资讯网（cninfo）的 15 份年报 PDF，5 家公司 × 2021–2023 三年（贵州茅台、五粮液、宁德时代、海康威视、中国平安），共 84.3 MB。

**追问：规模这么小，能叫企业级？**
语料规模是**刻意**保持在最小验证集，为了让全链路分钟级可复现（建索引约 0.35 元、5–10 分钟）。但每个环节的实现按生产标准处理：元数据过滤、混合检索融合、可开关的 rerank 与查询改写、引用溯源、拒答约束、指标评估、回归守卫。**"小语料 + 严格实现"比"大语料 + demo 实现"更有信息量**，这句话可以直接说给面试官。

### Q2. 整条链路的输入输出规模

**答**（全部本机核对过）：

| 环节 | 产物 | 实测规模 |
|---|---|---|
| 下载 | `data/raw_pdf/` | 15 份 PDF，84.3 MiB |
| 解析 | `data/parsed/*.json` | **43,048** 个 block，类型分 text / table / title，带 page_num、section_path、is_ocr |
| 分块 | `data/chunks/all_semantic.json` | **7,931** chunk，平均 **526** 字符 |
| 索引 | `vectorstore/faiss_index.bin` | 7,931 × **1024** 维，30.98 MiB；`faiss_meta.json` 11.61 MiB |
| 服务 | FastAPI | `/health`、`/query`、`/query/debug` + 静态前端 |

单份文件的 chunk 数从 454（中国平安 2023）到 1,124（宁德时代 2023）不等 —— 年报厚度和表格密度差异很大。

**追问：为什么 chunk 平均才 526 字？**
语义分块的边界由章节和表格决定，不是按字数硬切。526 是"一个自然小节"的均值，不是设计目标。真正影响检索质量的是块内语义是否完整 —— 我在 CI 基线里把 chunk 总数和维度钉成断言（7931 / 1024），就是防止重建时静默少一半。

### Q3. PDF 解析为什么难，你怎么处理的

**答**：年报是**排版复杂、机器可读性差**的典型文档。用了两个解析器交叉：

- `pdfplumber` 提表格（它对线框表格的还原能力更强）
- `PyMuPDF` 提带字体信息的文本 —— **靠字号和加粗判断标题层级**，这是 `pdfplumber` 弱项（`src/parse_pdf.py:164` 的设计说明）

`AnnualReportParser` 同时打开两个文档，逐页对齐，产出统一的 block 列表，并维护一个**章节栈**（`src/parse_pdf.py:174`）：按「第X章 / 第X节 / 一、」这类中文序号正则推断层级，把 `section_path` 拼成 `公司 > 第十节 > 二、财务报表` 这样的路径字符串，用于溯源展示和过滤。

**追问：哪里做得不好？**
两处我很清楚：
1. **章节路径里混进了页眉页脚噪声** —— 实测引用串长这样：`1 / 143 > 第十节 > 二、 财务报表`，页码"1 / 143"被当成标题压进了栈里，还有 `二、非持续的公允` 这种被截断的标题。根因是标题识别只看字号/加粗，没做"整行是否像页眉"的判别。
2. **扫描版页面走 OCR，但 OCR 在这台机器上没跑通过** —— `tesseract-ocr` 二进制没装，只有 `pytesseract` 包。所以 `is_ocr` 这条分支我**没能端到端验证**，这是诚实的边界。

### Q4. 三种分块策略的区别与取舍

**答**（`src/chunk_documents.py`）：

| 策略 | 做法 | 问题 |
|---|---|---|
| `fixed` | 按字符数切，`step = chunk_size - overlap` | 无视句子/表格边界，表格被切断 |
| `semantic` | 按 block 结构：遇 title 强制切块，table **单独成块**，正文累积到 max_chunk_size | 块大小不均匀（财报一个大表格可能很大） |
| `hierarchical` | 父子两级：父块 2000 字供上下文，子块 400 字供检索（Small-to-Big） | 页码对应关系复杂，源码里刻意把 `page_num` 置 -1 |
| `structured` | 按 `section_path` 建章节树（显式 H1/H2/H3）；父块单独存 `parents.json`，子块只留 `parent_id`；表格子块=摘要+原始 Markdown，`table_json` 保留二维结构 | 100 题整体仍不如 semantic（Hit 0.520 vs 0.550），仅数值题 + 重排时占优 |

**默认选 semantic**，因为年报有清晰的章节结构可用，而表格独立成块能避免 embedding 被大量数字稀释。

**追问：Parent-Child 的父块是怎么存的？**
`structured` 策略已经修掉 hierarchical 的冗余设计债：父块单独写 `data/chunks/all_structured_parents.json`，建索引时拷到 `vectorstore/structured/parents.json`；子块只带 `parent_id`。检索时 `resolve_chunk_content` 按 `parent_id` 查父块表（查不到才退回内联 `parent_content` / 子块自身），即"子块召回、父块拼装"。当前主索引仍是 semantic，切 structured 用 `RAG_INDEX_DIR` 或 `--index-dir`。

**追问：分块时重叠真的有用吗？**
在 `fixed` 里有用（切断句子时靠 overlap 补回上下文）；在 `semantic` 里没有 overlap，因为切点是语义边界。这也是为什么 `fixed` 策略下相邻块前 10 字必然相同（我用单测钉住了这个行为）。

### Q5. Embedding 用的什么，为什么选它

**答**：阿里云 DashScope `text-embedding-v3`，**1024 维**，通过 OpenAI 兼容接口调用。检索前把向量做 L2 归一化（`src/rag_pipeline.py:106`），所以 FAISS 用内积索引就等价于余弦相似度。

选它的理由：中文语料效果好、有 OpenAI 兼容接口（换供应商只改 base_url）、按量计费便宜。整个索引重建 **7,931 个 chunk 约 0.35 元、5–10 分钟**。

**追问：为什么不本地跑开源 embedding？**
本机 torch 是 `2.14.1+xpu`（Intel XPU 构建），跑本地 embedding 模型的吞吐不如调 API，而且项目已经必须为 rerank 装 `sentence-transformers`。**但 reranker 我是真放在本地跑的**（`bge-reranker-base`，1.1 GB），因为它对中文精确数字的召回质量影响很大，而 API 侧没有对等的 rerank 服务。

**追问：向量库为什么用 FAISS 而不是 Chroma？**
两个都实现了（`build_index.py` 能同时建 FAISS 和 chroma 索引做对比）。选 FAISS 做主力是因为：10K 级向量纯内存暴力检索已经够快（实测 `index.search` 亚毫秒级），不需要索引构建开销和额外服务；元数据我另存了一个 JSON 做过滤，比让向量库管元数据更可控。语料再大一到两个数量级才需要 IVF/HNSW 或专门的向量库。

### Q6. 检索链路详细讲一下

**答**：双路召回 + RRF 融合 + 可选重排 + 元数据过滤。

```
问题 →（可选 LLM 查询改写，qwen-turbo）
     ├─ 向量召回 top 10（多取 4 倍再过滤，src/rag_pipeline.py:121）
     └─ BM25 召回 top 10（jieba 分词 + rank_bm25）
     → RRF 融合（k=60）→ 取 top 4 →（可选 CrossEncoder 重排）→ 给 LLM
```

**RRF 公式**：`score(d) = Σ 1/(k + rank_i(d))`，k=60 是经验值。只用排名不用原始分数，所以天然规避了"余弦相似度和 BM25 分数量纲不同没法直接加权"这个问题。

**追问：为什么两种检索都要？**
互补盲区。向量检索擅长"经营情况怎么样"这类语义模糊问法，但对**精确数字和专有名词**弱（"研发费用率"这种词可能被 embedding 拉偏）；BM25 反过来。实测里 `precise_number` 类问题靠 BM25 才召得回具体金额。

**追问：BM25 每次都要重新分词整个语料库？**
是的，这是当前实现的一个真实性能问题。`BM25Store.__init__` 对 7,931 个块做 jieba 分词再建 `BM25Okapi`，**实测 9–12 秒**，服务冷启动的主要成本就在这。生产做法是把倒排索引持久化（`rank_bm25` 本身不支持，需要换 `tantivy`/`whoosh` 或自建）。我在 CI 里也因为这个耗时提供了 `--fast-index` 开关（0.13 秒，只做元数据比对）。

**追问：k=60 为什么是 60？**
RRF 论文的推荐值。直觉是：k 相当于"排名的衰减刚度"，k 太小则 top1 权重压倒性，太大则所有排名几乎等权。我的单测直接按公式手算钉住了 `1/61 + 1/62` 这类值，改 k 必红。

### Q7. 元数据过滤怎么实现的？这里你是不是修过一个 bug

**答**：修过，而且这是这个项目我最能讲的一个调试故事。

**症状**：用户在 API 上明确传了 `stock_code=600519, year=2023`，但返回的引用里出现了 `600519_2022_00205`（2022 年报，第 52 页）。

**定位**：过滤只在一路召回上生效 —— `RAGPipeline.query` 里向量检索传了 `filter_meta`（`rag_pipeline.py:360`），但 `BM25Store.search(query, top_k)` **压根没有 filter 形参**（`:160`）。而 `use_bm25=True` 是默认路径（`serve.py:55-56` 就是这么构造的），于是 RRF 把没被过滤的那一批候选照常混进上下文。

**修法**：
1. 抽出共享谓词 `match_filter(item, filter_meta)`，向量侧改调它 —— 关键是**两条链路必须同源**，否则以后各自漂移。
2. BM25 侧不重写排序，而是把不合规块的分数 `np.where(keep, scores, 0.0)` 置零，**复用下面本来就有的 `scores[idx] < 1e-9` 跳过逻辑**。这样不引入新的截断/回填行为，改动面最小。
3. 补齐两个调用点：主链路和 `/query/debug`。

**验证**（三层，不是我说了算）：
- 真实语料：同一条探针，无过滤 top10 横跨 `{2021,2022,2023}`，加 `{year:2021}` 后只剩 `{2021}`；
- 端到端 HTTP：修复前那条请求的 4 个引用混着 2022，修复后全是 `_2023_`；
- 单测 13 条，其中**两条是 AST 静态守卫**，直接检查调用点有没有把 filter 传下去 —— 因为只测函数能力的话，删掉调用点实参照样全绿，而那正是缺陷原样。

**追问：这个 bug 为什么测试一开始没抓到？**
因为最初的单测全在合成语料上测 `BM25Store.search` 本身（能力是有的），没人测"接线"。发现这点后我补了 AST 守卫，并把它写进了 CI 的规矩：**能力测试必须配一条接线测试**。

### Q8. Rerank 用的什么？效果怎么验证的

**答**：`BAAI/bge-reranker-base`（CrossEncoder，双向注意力），对 RRF 后的候选做二次精排取 top 4。它比 bi-encoder 准，因为 query 和 document 在同一个注意力里交互，但**只能小批量用**（每一对都要过一次模型），所以只能对 10 条候选做，不能对 7931 条做。

模型缺失时**自动降级为直接截断**（`src/rag_pipeline.py:238`），不抛异常 —— 这是刻意的可用性取舍：宁可精排缺失，也不要整服务起不来。

**追问：效果提升多少？**
现在有数了（v2 题集 **100 题**，`measure_rerank_100_20261107b.log`）：

| 口径 | Hit@4 | MRR@4 | 上下文字符 |
|---|---|---|---|
| 基线（RRF top4） | **0.560** | 0.312 | 3306 |
| 重排 top4（不过滤） | 0.550 | **0.330** | 4158（+25.8%） |
| 重排 + 下限 0.70 | 0.410 | 0.261 | 2778（−16.0%） |
| 重排 + 下限 0.90 | 0.270 | 0.190 | 1901（−42.5%） |

MRR@4 **绝对 +1.8pp、相对 +5.8%**；但 Hit@4 反而 −1.0pp。25 题子集上曾看到
"重排 + 0.70 质量不掉、字符 −11.1%"，扩到 100 题后**该结论被推翻**：0.70 时
Hit 掉到 0.410。0.30~0.90 每一档下限都在损失命中，没有任何阈值能同时保住
Hit 和削减上下文 —— 所以线上改为**打开重排、默认不设下限**（`RERANK_MIN_SCORE`
未设置即 None）。若面试被问"怎么用阈值削减 Token"，正确回答是：机制在，
但在这份语料上找不到既保质量又减上下文的拐点，不拿质量换比例。

**这里我还翻了自己两个认知错误，值得当故事讲：**
1. 我原以为旧 `rerank()` 有"过滤长尾低分文档"的能力 —— 实际它**只排序+截断，永远返回 top_k**，
   所以"重排削减上下文 Token"在旧代码下恒为 0%。简历那句话描述的是一个不存在的机制。
2. 我原以为消融脚本"跑不起来"（路径不一致）—— 实际它有回退逻辑能跑；
   但回退**对任何策略都拿 semantic 索引冒充**，会产出标着 "fixed/hierarchical" 的假结论。
   静默错比崩溃危险，已改成只有 semantic 允许回退。

**追问：那代价是什么？**
稳态请求从 2.5 s 涨到 3.75 s（约 +1.2 s，10 对候选的 CrossEncoder 推理）。
另外旧实现**每次请求都重新加载 1.1 GB 模型（实测 5.8 s/请求）** —— 这大概就是当初
`serve.py` 把精排关掉的真实原因；我改成进程级单例后这个成本只付一次，且服务冷启动不受影响
（懒加载，不在 lifespan 里，实测冷启动仍 11 s）。
评估路径 `evaluate.py` 目前**仍不开精排**，所以那批 ragas 数字是不带重排的口径。

### Q9. 生成侧的提示词怎么写的，怎么防止幻觉

**答**（`src/rag_pipeline.py:57`）system prompt 五条硬规则：

1. 只根据【参考资料】回答，不得引用或编造资料外数据
2. 资料不足时**直接说**"根据提供的资料无法回答此问题"
3. 引用具体数据时句末标来源编号，如 `营业收入为1476亿元[1]`
4. 数字要精确，不得四舍五入或模糊表达
5. 回答简洁

模型 `qwen-plus`，**`temperature=0.1`**（`src/rag_pipeline.py:329`）—— 刻意接近确定性：财报问答里同一问题今天给"1476.94 亿"明天给"1477 亿"都是不可接受的，而规则 4 又要求数字精确不得四舍五入，采样温度必须压住。留 0.1 而不是 0，是因为完全贪心解码在多来源的综合表述上容易生硬。

**追问：怎么保证引用编号真的对应到来源？**
`_build_source()` 把 chunk 元信息格式化成 `600519 2023年报 · 第十节 > 二、财务报表 · 第61页` 这样的字符串塞进上下文，LLM 输出的 `[n]` 与 citations 数组同序返回。**但这是"约定"而不是"校验"** —— 我没有做"输出的 [n] 必须能在上下文中找到"的后置检查，模型理论上可以标错编号。这是个真实缺口，能答出来比假装没有更好。

**追问：拒答是怎么实现的？评测里怎么算它对？**
靠 prompt 规则 2，没有硬编码判断。v2 评测集里有 **25 道 `refusal` 题**（如问 2027 年业绩指引、高管个人财富、股价和投资建议 —— 年报里根本没有），这类题**被排除出 RAGAS 打分**（`evaluate.py`），因为 ground_truth 是描述性的"应该拒答"，不适合 faithfulness 这类指标。

拒答单独用 `src/refusal.py` 三分类：`refused_with_context`（有上下文但模型明确说资料不足）/ `empty_context`（检索为空，属于检索失败不是模型拒答）/ `answered`。`scripts/ci/measure_refusal.py` 实测（2026-11-07，served 与 eval 两种配置）：**25/25 真拒答、0 空检索、可判定题拒答率 100%**。这个口径比旧版"关键词命中率"严格：旧版会把 `n_ctx=0` 的"未找到相关内容"也算成拒答，属于把检索问题记在生成头上。

### Q10. 评估体系怎么设计的

**答**：两层。

**第一层：RAGAS 四项指标（LLM 裁判）**

| 指标 | 测什么 | 靠什么算 |
|---|---|---|
| Faithfulness | 答案是否完全来自检索内容（有无幻觉） | LLM 判断 |
| Answer Relevancy | 答案是否切题 | Embedding 相似度 |
| Context Precision | 检索内容中有用的比例 | LLM 判断 |
| Context Recall | 需要的内容被检索到了多少 | LLM 判断 |

**评测集有两代，`--question-set` 可切（默认 v2）**：

- **v1（20 题，5 类）**：`simple_fact`×5、`precise_number`×5、`cross_doc_compare`×4、`time_trend`×3、`should_refuse`×3。ARCHITECTURE.md 那批数字是在它上面得到的，保留作旧口径退路。
- **v2（125 题，4 类）**：`numeric` 36 / `multihop` 34 / `hallucination` 30 / `refusal` 25。由摘要区数据派生 + 三道锁验证（见 Q10b）。

裁判 LLM 默认小米 MiMo Token Plan 的 `mimo-v2.6-flash`，可切回 DeepSeek；embedding 恒走 DashScope（**MiMo 没有 embeddings 端点，而 answer_relevancy 要算向量相似度**，这是硬约束不是偏好）。

**第二层：消融实验（不依赖 LLM，快）**
`compare_strategies.py`：3 种分块策略 × 3 种检索方式 = 9 种组合，指标 `Hit Rate@4` 和 `MRR`。**设计好了但我没跑**，所以我不报这层的任何数字。

**追问：为什么 LLM 裁判和指标计算要分档可切换？**
因为**换裁判等于换尺子**，这点我实测到了：同一批 20 题，DeepSeek 裁判给的是 F 0.775 / AR 0.633 / CP 0.273 / CR 0.382，MiMo 裁判给的是 **F 0.868 / AR 0.625 / CP 0.199 / CR 0.445**。忠实度更宽松、上下文精度更苛刻。如果只报一组数字，那组数字就不可解释 —— 所以档位必须显式可切、可复现。

### Q10b. 125 道题的 ground truth 是怎么来的？（这题几乎必被追问）

**答**：不是我写的，是从年报摘要区**派生**出来的，并且过三道锁。因为手写 100+ 道题的数字，
只要有一个抄错，faithfulness/recall 就在测一个错误答案 —— 而且不会报错。

**三道锁**：

1. **区域锁**：只认「主要会计数据 / 主要财务指标」摘要区（锚点页 ±3 页 / 前 15 页 / 锚点块后 40 块）。
2. **引用锁**：每题的 `evidence.quote` 必须是**原文逐字子串**；标签和数值被解析到不同块时，
   拆成 label_quote + value_quote 两段，各自逐字。
3. **一致锁**：一个值要被接受，必须 B1（≥2 份不同年报一致，典型是"2022 年报的本年列 == 2023 年报的上年列"）
   或 B2（同一份年报的 ≥2 个不同块里出现，摘要表 + 正文/利润表）。
   实测 134 条候选 → 接受 71 条（B1 46 / B2 25），**拒绝 12 条无佐证**。

**为什么不用正则直接抓正文数字** —— 三条实测反例，正则全会中招：

| 抓到的东西 | 真相 |
|---|---|
| 五粮液 2023 正文 `净利润140.45亿元` | 不是它的归母净利（302.11 亿） |
| 宁德时代 `营业收入 100.00%` | 是"纳入评价范围单位占比"，不是营收 |
| 海康威视 `母公司实现净利润10,552,055,515.88元` | 母公司口径，不是合并口径 |

**校验器刻意不 import 生成器**。理由：如果校验器复用生成器的解析逻辑，它只是在跟自己对齐，
生成器的 bug 会被原样继承 —— 这个项目已经因为"测试全绿但分支没跑到"翻过两次车。

**追问：这套流程里出过什么错？**
三个都被工具当场抓到：
1. `hi, lo = (a, va)` 我以为是赋元组，其实是解包 → `hi` 变成公司代码字符串、`hi[1]` 是它的第二个字符，
   ground truth 会静默变成"0 为 2…"。靠 float 格式化报类型错才发现。
2. 校验器把 6 位股票代码当财务数字校验，误报 39 条"答案数字找不到出处"。
3. 一致锁的 B2 判据原本是假的：`{f for (f,_) in idx if f == same_file}` 过滤后长度恒为 1，
   永远不成立；改成按 `(file, block)` 去重才真在数"同文档多处"。

**追问：五家公司都覆盖了吗？**
**没有，中国平安 0 条派生题**。它的摘要表被解析成碎片，而且 page≤15 内有多处 `营业收入` 标签
指向分部数据而非合并营收（实测抓到 253,778 这个错值），候选全部没过一致锁 → 被丢弃。
我的选择是**宁可不给题，也不给可能是错的 ground truth**，并把这件事写进
`questions_v2.json` 的 `coverage.companies_without` + `why`，
再用一条守卫校验"声明"与"实际出题公司"一致（谎报会红）。
所以准确说法是：**125 题 = 4/5 家公司的派生题 + 全部 5 家的拒答题**。

### Q10c. 领域词表做了什么，效果如何？

**答**：加了 157 词的 A 股术语词典（`src/domain_dict.txt`），在两条 BM25 链路加载前注入 jieba。
实测 157 词里 **126 个确实被默认 jieba 切碎**（`归属于上市公司股东的净利润 → 归属于/上市公司/股东/的/净利润`）。

**但收益我目前不能报数字。** 在 v1 的 17 题上做了跨进程 A/B（jieba 词典是进程级全局的，
同进程 A/B 做不到），结果方向不一致：

| 口径 | Hit@4 | MRR@4 |
|---|---|---|
| BM25 单路 + 全量词表 | +5.9pp | −8.3pp |
| BM25 单路 + 精简词表 | −5.9pp | −13.2pp |
| 混合检索 + 全量词表 | −5.9pp | +4.4pp |

每个差值都只有 1 题的量级（1/17 = 5.9pp），**n=17 下不具备统计意义** ——
后来我用 v2 的 **100 道派生题**重测，得到了确定答案：**净效果为零**。

| 口径 | Hit@4 开表/关表 | MRR@4 开表/关表 |
|---|---|---|
| BM25 单路 | 0.380 / 0.400（−2.0pp） | 0.196 / 0.220 |
| **混合检索（线上口径）** | **0.540 / 0.540（±0.0pp）** | 0.3125 / 0.3058（+0.7pp） |

原因可指认，不是"测不出"：词表**修好 5 题** —— 全是长复合标签被切碎导致
**top1 命中错公司**（问 000858 的净资产，关表时 top1 是 `300750_2023`），
这正是"切词粉碎"这个真实缺陷；同时**弄坏 5 题** —— 集中在跨年趋势题，
整词化减少了可匹配 term 数、召回面收窄。混合链路里两者恰好抵消。

所以我的结论是：**机制保留**（它消除的是"答错公司"这种用户可感知的硬错误，
产品代价高于趋势题的排名变化），**但绝不给词表配收益百分比**。
而上一轮 n=17 看到的"方向不一致"确实只是噪声 —— 这个自我修正本身就是我想讲的点。

**追问：那简历上"防止切词粉碎"怎么说？**
机制成立、案例可指认（能现场演示一句 query 的切分差异），但**不能配百分比**。
另外简历原话"在 Embedding 环节加入领域词表"技术上不准确 —— 领域词表作用的是**中文分词/关键词召回**，
embedding 的分词在模型内部，外部词典影响不到它。这句应该改。

### Q11. 讲一个你印象最深的评估发现

**答**：**"Context Precision 0.199 很糟糕"是一个错误的结论，正确的结论是"三类需要多块组合的问题，上下文里根本没有正确内容"。**

一开始只有均值，看不出所以然。我做了逐题分数落盘，然后按题型归因：

| 题型 | n | Faithfulness | Answer Relevancy | **Context Precision** | **Context Recall** |
|---|---|---|---|---|---|
| simple_fact | 5 | 1.000 | 0.977 | 0.478 | 0.900 |
| precise_number | 5 | 0.758 | 0.594 | **0.200** | 0.400 |
| cross_doc_compare | 4 | 0.802 | 0.205 | **0.000** | **0.000** |
| time_trend | 3 | 0.917 | 0.651 | **0.000** | 0.357 |

三个结论：

1. **基础检索是健康的** —— simple_fact 的 CP 0.478、CR 0.900，说明单点事实找得到。
2. **对比题和趋势题 CP 和 CR 同时为 0** —— 这是关键信号：CR=0 说明"标准答案需要的内容没进上下文"，CP=0 说明"进来的内容里没有一句有用"。**同时为 0 意味着这不是排序问题，是召回集合问题**。根因很具体：对比题要同时命中两家公司的块、趋势题要跨 2021/2022/2023 三年，而上下文预算只有 4 块，装得下一家就装不下另一家。**这是结构性缺陷，调 rerank、调 k 值都救不了。**
3. **precise_number CP 只有 0.2** —— 具体金额都在表格里，而项目里有个已知问题：表格内容被同时写进 `table` 和 `text` 两种块，**约 4,491 个块是重复的**。重复块挤占了 top-4 的有效位置。

**追问：那你会怎么修？**
对比/趋势题走**分组召回**：识别出问题里的多个实体/年份，每个各取 top-k，再进 RRF 合并，并按题型放大上下文预算。表格重复则是分块层的问题 —— 表格块存在时就不该再把它的内容铺进 text 块。这两条都会改变检索语义和已有结论，所以我先写方案不动代码。

**追问：这个归因的前提是逐题分数可信，你怎么知道的？**
我让归因工具自带自检：用逐题分数**重算均值**，和顶层存的均值比对。全量 17 题四个指标全部一致（0.8676 / 0.6251 / 0.1993 / 0.4454 分毫不差）。这一步很有必要 —— 逐题分数是按 dataset 行序 zip 回填的，**错位一格不会报错，只会悄悄给出错误的结论**。

### Q12. 服务的部署形态和已知局限

**答**：FastAPI + uvicorn，`lifespan` 里构造 pipeline（`serve.py:51`），三个端点：`GET /health`、`POST /query`、`POST /query/debug`（后者返回向量召回/BM25/RRF/最终上下文四段中间结果，是排检索问题的主力工具），加一个静态前端。

**已知局限我列五条**，这些都是我实测或读代码确认的：

1. **CORS 是 `allow_origins=["*"]`**（`serve.py:76`），且**接口没有任何鉴权** —— key 在服务端，任何人能访问就能白烧我的 API 额度。生产必须加。
2. **BM25 索引在进程内常驻**，每副本 9–12 秒启动成本，不能水平扩容时反复重建。
3. **`/health` 不校验 key 有效性** —— `get_client()` 只构造 OpenAI 客户端、不发请求。塞一个占位 key 服务照样 200。我在 CI 里专门加了占位符识别来堵这个假绿。
4. **同步端点**（`def query`，不是 `async def`），检索是阻塞 IO，并发能力有限。
5. **单次问答成本不透明** —— 一条问答要 1 次 embedding + 1 次生成（改写时再多一次），我没有埋 token 统计。

**追问：为什么不部署到公网？**
这是本地验证型项目，语料和索引都在 gitignore 内（150 MB 数据 + 56 MB 索引 + 1.1 GB reranker），部署意味着要么重建（花钱、且要爬 cninfo）要么走 LFS。**我把工程投入放在了"可复现"而不是"可访问"上** —— 这也体现在 CI 选型上（见下一部分）。

## 第二部分：CI/CD

### Q13. 你的 CI/CD 是怎么设计的，为什么不用 GitHub Actions

**答**：**纯本地**，四道门 + git 钩子自动触发 + 110 条回归守卫。

| 门 | 查什么 | 实测耗时 |
|---|---|---|
| 静态 | 8 个文件 `py_compile` + 单进程 import 冒烟 | 5 s |
| 索引 | 13 条断言：7931×1024 自洽、必需字段存在、评测集题数与题型分布、真实 BM25 检索命中、**元数据过滤在真实语料上生效** | 26 s（`--fast` 0.13 s） |
| 单测 | 110 条纯函数与数据守卫 | 8 s |
| 服务 | 拉起 uvicorn → 轮询 `/health` 到 200 → 关停并确认端口释放 | 14–32 s |

全套 `run_all --tier p0p1` 约 35–80 秒。

**为什么本地而不是云端，三条硬理由**（都是实测出来的，不是偏好）：
1. **大产物全在 gitignore 内**：`data` 147 MB、`vectorstore` 56 MB、`models` 1.1 GB。云端 runner 拿不到，任何检索/评估档都得先重建 —— 重建要爬 cninfo 还要烧 embedding 费。**本地直接读现成的，索引门和真实检索这两档在本地几乎零边际成本，在云端做不到。**
2. **本机有非标准的 torch 构建**（`2.14.1+xpu`，Intel XPU），云端 `pip install -r requirements.txt` 装不出等价环境，rerank 行为可能不一致。
3. 单人项目，**换不来的那部分（PR 门禁、第三方证据）价值有限**。

**追问：那本地方案放弃了什么？**
放弃"全新环境装不装得起来"的即时保证（用每周/改依赖时的一次性干净安装补偿）、PR 门禁、`--no-verify` 的防御、以及机器挂了记录就没了。这些我都清楚，且第一项目前用 P2 档的计划任务补偿。

### Q14. 退出码和输出为什么这么设计

**答**：三档语义，**关键是 2 和 1 必须分开**：

| 码 | 含义 | 为什么重要 |
|---|---|---|
| 0 | 通过 | —— |
| 1 | **断言失败，真回归** | 需要立刻定位 |
| 2 | **前置缺失**（没 key / 没索引 / 没 pytest） | **不是代码问题**，混进"失败"会让人去查错方向 |

比如服务门：没 key 时 uvicorn 必然退出码 3、`/health` 连接被拒 —— 实测过。如果把这判成"测试失败"，人会怀疑自己改坏了代码，其实是环境没配。所以它报 SKIP + 退出码 2，并直接把重建命令打出来。

**输出纪律**：成功也要打一行摘要。**"没输出"绝不能等于"没跑"** —— 这个项目吃过教训：Windows 上 `core.filemode=false` 导致 clone 后钩子丢可执行位，**Git 不报错，就是不执行**。所以配了自检命令（`git ls-files -s` 应显示 `100755`）和 `.gitattributes` 钉 `eol=lf`（否则 autocrlf 把钩子变成 CRLF，`sh.exe` 读到 `#!/usr/bin/env sh\r` 直接 bad interpreter）。

**追问：逃生阀为什么留？**
`CI_SKIP=1` 可以跳过，但会打印醒目警告并在结果 JSON 里留缺口。不放逃生阀的话，赶工时你会直接用 `--no-verify` —— 那个连日志都不留，反而更失控。

### Q15. 110 条测试都测什么？怎么保证测试本身不是空转

**答**：全部**零密钥、零网络、不读大产物**，这样它们才可能秒级跑。分布：分块策略、引用格式化纯函数、RRF 公式、指标计算数学、元数据过滤、逐题落盘、裁判配置解析、探针失败分类、归因工具。

**测试本身的可信性靠两件事：**

**一、每条新守卫都做反向验证** —— 故意把被测代码改坏 → 确认断言必红 → 还原 → 与原文件 **sha256 逐字节一致**。累计做了 18 处变异。举几个例子：

| 改坏的东西 | 该拦住它的守卫 |
|---|---|
| `build_chunk_id` 补零 `%05d → %04d` | 单测 |
| RRF 默认 `k=60 → 40` | 单测（按公式手算比对） |
| `compute_metrics` 的 `[:top_k] → [:top_k*2]` | 单测（会让 hit_rate 虚高） |
| BM25 分数掩码被摘掉 | 单测 |
| **调用点丢掉 filter_meta 实参** | AST 接线守卫 |
| baseline 条数 7931 → 7000 | 索引门 |
| 探针里 `if not content` 短路 | 探针守卫（防它变假绿灯） |

**二、每条断言都要有"空断言检查"** —— 也就是对照组。举例：索引门里"加了 year=2021 过滤后只剩 2021"这条，如果不加过滤的结果本来就全是 2021，那它是**空断言**，永远绿却什么都没测。所以我配了第二条"无过滤确实跨年"作为对照，两者同时成立才有意义。

**追问：反向验证里出过岔子吗？**
出过，两类都有价值：
1. **变异脚本自己写错**：第一次跑反向验证，我把 `rm -f` 之类删掉了，但更严重的是有一处**替换的是相邻的行而不是目标行** —— 结果测试正确地保持绿色，我一开始以为"守卫无效"。真相是变异根本没改动任何行为。**判红要用退出码，不能靠匹配 "1 failed" 字符串**（计数行在 warnings 块之前，字符串匹配会误判）。
2. **CRLF 匹配失败**：现有源文件工作副本是 CRLF，我的多行匹配串用 `\n` → 匹配不到。核实过 `HEAD` 里存的是 LF（`core.autocrlf=true` 已归一化），所以改成单行匹配。

### Q16. 说一个"测试全绿但有 bug"的真实案例

**答**：有两次，我都能具体说清是哪一行。

**案例一（更严重）**：归因工具 `analyze_scores.py` 里有个 `NameError` —— 嵌套推导式中引用了不存在的变量 `k`。**6 条测试全绿，一接真实数据就崩**。原因很明确：所有测试都显式传了 `--file`，**"自动发现最新产物"那条分支一次都没被执行过**。修复后我补了 4 条测试专门覆盖这条分支，包括"只有旧格式产物时应判 SKIP 而不是崩"和"半截 JSON 不能整体搞挂"。

**案例二（同类）**：给索引门写断言时，我取 `company_name` 和 `block_type` 两个字段 —— 但 `faiss_meta.json` 里**根本没有这两个键**（真实字段是 `block_types` 复数）。用 `.get()` 取到 `None` **不报错、断言静默通过**。所以 P0-2 定了一条规约：**断言前必须先校验字段存在性，禁止裸 `.get()`**。这类问题和前端里 `getElementById` 指向不存在的 id 又被 `?.` 吞掉是同一种事故 —— 逻辑跑了，但什么都没验。

**教训一句话**：绿色的测试不等于有效的测试。判断标准是"我能不能证明把代码改坏时它会变红"。

### Q17. CI 里有没有测花钱的那部分？怎么控制成本

**答**：花钱档**故意不进钩子**，单独用 `run_eval.sh` 触发，而且做了三层成本控制：

1. **裁判连通性探针**：真正评估前发一次约 45 token 的请求，断言能拿到非空 content。为什么必要 —— MiMo 是思考型模型，实测发现小 `max_tokens` 时它会**把回答全放进 `reasoning_content`、`content` 返回空串**，ragas 拿不到判定文本。这种失败如果在全量跑完之后才暴露，就是白烧 6.5 分钟和一批 token。探针的退出码分档也刻意区分：鉴权/网络/模型 ID 问题判 2，**连通但 content 为空判 1**（环境没问题，是模型输出形态不能用）。
2. **评估脚本侧预检**：`main()` 在建索引、生成答案之前就校验 key 和档位，缺 key 直接退出 2。因为全量 20 题实测 **393 秒**且要花钱，顺序错了就是白跑。
3. **档位可切换**：冒烟用 `--question-ids 1,2,3`（实测 32–105 秒），全量才 393 秒。探针输出预算下限（512）也被测试钉住 —— 用小预算探出来的"空 content"是参数的锅，会把好配置误判成坏。

**追问：为什么不测端到端问答质量？**
测了但只到冒烟层：服务门验装配，`/health` 200；真实 `POST /query` 我手工端到端验过（答案正确、2.5 秒、引用 4 条），但**没做成每次提交都跑的自动化**，因为它花钱且要联网。这是我知道的取舍。

### Q18. 这个项目里 CI/CD 帮你发现过什么真实缺陷

**答**：四个，都不是"我觉得可能有"，是跑出来的：

1. **依赖不锁版本导致 `import ragas` 直接失败。** `requirements.txt` 全是 `>=`。实测今天重装会拿到 ragas 0.4.3 / torch 2.15.0 / pandas 3.1.0；而本机是 ragas 0.3.1 + langchain-community 0.4.2 —— 后者删了 `chat_models/vertexai`，而 ragas **从 0.2.15 到 0.4.3 全版本都顶层硬 import 它**（我扫了三个版本的 wheel）。所以升 ragas 没用，只能钉 `langchain-community==0.4.1`。修法我验证过：把 0.4.1 用 `--target` 装进临时目录、靠 `PYTHONPATH` 抢在 site-packages 前面（**不动 env**），import 全链路通过。
2. **PyMuPDF 的 `fitz` 别名会往 stdout 打警告**，我最初用 stdout 传 JSON 给 shell 就被它污染，导致静态门误报。根治：`import fitz → import pymupdf`，并验证等价性（最小的那份 PDF 现场解析 803 blocks，与旧落盘结果块数一致）。
3. **`serve.py` 用了 Pydantic V2 废弃的 `Field(example=...)`** —— pytest 报 3 条告警。改 `json_schema_extra` 后告警归零，且我核对了 OpenAPI 三个 example 和 `required` 都没变（改这种"UI 承诺"必须验证前端还在）。
4. **`evaluate.py` 不读 `.env`** —— CI 的 shell 载入器覆盖不到直接 `python evaluation/evaluate.py` 这种手动跑法，实测撞 `OSError` 退出码 1。已补 `run_eval.sh` 作为正式入口。

**追问：CI 有没有抓到你自己写的 bug？**
有，而且不少。举两个：服务门最初用 `( cd src && uvicorn ) &`，`$!` 是子 shell 的 pid，**kill 掉 shell 后 python.exe 仍占着端口** —— 实测泄漏过一次 PID 51388，改成 `PYTHONPATH` 注入 + 轮询端口确认释放。还有 `set -u` 下 `$CI_PY` 未定义直接炸；以及上面那个 `NameError`。

### Q19. 你这套 CI 的覆盖盲区在哪

**答**：直接说四条，别等面试官问：

1. **单测只测纯函数，没有任何真实数据参与**（合成语料 6 条 + monkeypatch 检索）。所以"代码逻辑对但数据形状变了"这类问题，只能靠索引门那 13 条断言兜，兜不住的部分就是盲区。
2. **PDF 解析和 OCR 没有回归测试** —— 解析要跑真实 PDF，最小的那份也要 19 秒；OCR 分支在这台机器上根本无法验证（没装 tesseract）。
3. **消融实验没跑过**，所以"semantic vs fixed vs hierarchical 到底差多少"我没有数据，只有脚本。
4. **端到端问答质量不进钩子**（花钱），所以一次改动让答案质量下降但没弄坏代码结构，CI 会放行 —— 得靠人工评估档。

## 第三部分：会被追问的"弱点"及诚实答法

**Q20. 评测集在统计上站得住吗？**
**答**：分两代说。**v1（20 题）不够** —— 17 个有效样本拆到 5 个题型，最少的 time_trend 只有 3 题，
**单题均值就能移动整体 0.33**；我一开始只跑 2 题拿到 CP=0.5，全量是 0.27，
**小样本严重偏乐观，这是我实际踩到的**。领域词表的 A/B 也卡在这里：所有差值都只有 1 题的量级（5.9pp），
所以我不给词表报收益。

**v2（125 题）就是为了拿到分辨率而做的**：100 道派生题参与打分，单题影响降到 ~1pp 量级。
但它有两个我自己必须说清的局限：① **中国平安 0 条派生题**（摘要表排版碎片化 + 同名标签指向分部数据，
候选没过一致锁，我选择弃题而不是弃准确性）；② 派生题的题干是模板生成的，
自然度不如人工题，真实用户问法分布更广。

所以我给结论的原则没变：**结构性信号（对比题 CP 与 CR 同时为 0）在 n=4 上就足够确定，
但任何"0.199 vs 0.273 谁更好"级别的差异，我不会在 n 不够时下结论。**

**Q21. 只覆盖 5 家公司，泛化能力怎么证明？**
**答**：证明不了。当前语料下"检索不到"和"语料里没有"是同一个现象，系统无法区分 —— 拒答题就是专门用来探这条线的（3 题问股价和投资建议，年报里根本没有）。要答泛化，需要扩语料 + 加"应拒答"比例更高的对抗集。

**Q22. 为什么不用 LangChain/LlamaIndex？**
只用了 `langchain-openai` 的 wrapper（因为 RAGAS 需要它），检索、融合、分块全手写。理由：这条链路的每一步都是我要能讲清取舍的对象，套框架会把最有信息量的部分藏起来。RRF 自己写才 30 行，且我用单测按公式逐值钉死了。

**Q23. 如果并发 1000 怎么办？**
现在的形态扛不住，我知道瓶颈在哪：BM25 全量内存索引常驻（每副本 9–12 秒启动）、同步端点、rerank 是本地 torch 推理。方向：倒排索引持久化并换 tantivy、异步化、rerank 独立成服务或降级、FAISS 上 IVF/HNSW、加缓存层。**但我没做过压测，所以不给具体 QPS 数字。**
